## 镜头七：Rust 为什么要这样设计？

**时间：约 20 秒**

### 旁白：

看到这里，你可能会觉得：

为什么 Rust 要把一次普通的赋值设计得这么麻烦？

因为像 `String` 这样的数据，最终必须有人负责释放它占用的内存。

如果小明和张三都认为自己拥有同一份数据，那么当他们离开作用域时，就可能同时尝试释放同一份资源。

这可能导致 **Double Free（重复释放）**。

Rust 的解决办法很直接：

一份资源，只能有一个明确的所有者。

当发生 Move 时，释放资源的责任会转移给新的变量，原来的变量立即失效。

而 Borrow（借用）只提供临时访问权，并不会获得释放资源的责任。

这样，Rust 就能在没有垃圾回收器的情况下，把很多内存问题提前阻止在编译阶段。

并出现红色警告图标。

# 第二阶段：Double Free 风险

### 动画：

1. `xiaoming_key` 左侧出现：

```
离开作用域
```

标签。

1. `xiaoming_key` 消失。
2. Rust 释放资源的动画：

- String 数据对象开始变暗；
- 出现释放动画；
- 数据对象暂时消失。

1. 接着：

`zhangsan_key` 也出现：

```
离开作用域
```

标签。

1. 它尝试释放已经不存在的数据。

画面出现：

```
Double Free
重复释放同一份资源
```

并出现错误效果：

- 红色闪烁；
- 数据对象碎裂；
- 屏幕震动。

强调：

```
这就是 Rust 不允许两个 Owner 存在的原因。
```

（可以设计成盾牌、守门员等形象）

编译阶段检查所有权

## 情况一：Move

展示代码：

```rust
let xiaoming_key = String::from("电动车钥匙");
let zhangsan_key = xiaoming_key;
```

动画：

初始状态：

```
xiaoming_key
      |
      |
      v

String("电动车钥匙")
```

执行：

```rust
let zhangsan_key = xiaoming_key;
```

动画：

- 黄色钥匙图标从 `xiaoming_key` 移动到 `zhangsan_key`
- 原来的所有权连接断开

最终状态：

```
xiaoming_key
    ❌
 moved


zhangsan_key
      |
      |
      v

String("电动车钥匙")
```

说明：

```
所有权发生转移
新的变量负责释放资源
原变量失效
```

## 情况二：Borrow

旁白：

但是，如果张三只是想临时使用数据，而不是接管所有权呢？

展示：

```rust
let xiaoming_key = String::from("电动车钥匙");
let zhangsan_key = &xiaoming_key;
```

动画：

初始：

```
xiaoming_key
      |
      |
      v

String("电动车钥匙")
```

执行借用：

```
xiaoming_key
      |
      |
      v

String("电动车钥匙")
      ^
      :
      :
zhangsan_key
(reference)
```

要求：

- 小明和 String 之间保持黄色实线；
- 张三和 String 之间使用蓝色虚线；
- 张三不能拥有正式钥匙，只能拥有临时访问权。

显示：

```
Borrow
临时访问
不负责释放资源
```

# 实现要求

- 不要表现为 Rust 运行时检测 Double Free；
- Double Free 只作为“如果允许多个 Owner 会发生什么”的假设演示；
- Move 动画中始终只有一个正式 Owner；
- Borrow 动画中 Owner 不发生变化；
- 所有权使用实线表示；
- 借用使用虚线表示；
- 不要复制出两个真实数据对象；
- 不要让观众误解为 Move 会复制数据；
- 数据对象始终保持唯一。
